# Darius input geometry feasibility (read-only, 2026-11-13)

## Method and source

`node qa/darius-input-2026-11-13/geometry-study.mjs` reads the current source constants, uses the installed Three `PerspectiveCamera`/`Vector3` to project actual board corners, and writes `geometry-study.json`. Sources: `web/src/scene.ts` (fit, initial pose, camera transitions from `web/src/input.ts`), `web/src/config.ts` (48° pitch, board border), `web/src/power-controls.ts` (18% reserve and 0.8/1.5 drag cap), `web/src/game-hud.css` and `web/src/crazygames-opening.css` (canvas exclusions), `web/src/tutorial.ts` (gesture guide), and the 2026-11-13 Darius PRD. Board half extent is 2.278013 world units from the current metadata cell size 0.536003 and 0.25 border cells. FOV is 42°, fit margin 1.06.

The main canvas excludes 54 px at the top and 148 px at the bottom, hence 800×450 → 800×248, 1366×768 → 1366×566, 1920×1080 → 1920×878 CSS px. At landscape height ≤640 with visible player banners it can instead exclude 100+112 px (800×450 → 800×238). CrazyGames and tutorial CSS have other exclusions. Full viewport dimensions in the JSON are deliberately hypothetical. DPR does not change these CSS px calculations.

The initial pose is set at `boardHalfExtent × (0,1.65,-1.85)`, but OrbitControls fixes pitch to 48° and `fitCameraToBoard` raises the distance to the fit minimum. For the tested aspect ratios, initial classic view and maximum wheel zoom therefore coincide in the current code. A classic mode restore also targets `wholeBoardDistance`; billiards selected-piece and strike cameras use separate adaptive/0.6 distances and cannot be inferred from this board fit alone. Front camera azimuth is `(0,-1)`; diagonal is `(1,-1)/√2`.

## Results

These are maximum classic board zooms at current 18% reserve. Height is projected board world-corner AABB / canvas height. `R` is the minimum distance to a canvas edge among projected board corners and sample piece centers; it is a **conservative proxy**, not the true selectable-piece bound. Full power for every direction among these samples needs `p_max × D ≤ R` (linear), or `D√p_max ≤ R` (quadratic).

Front and diagonal produce the same projected height at the fitted distance for this square board and these aspect ratios, but diagonal needs 12.615 world-unit distance versus 8.920 front, making projected width smaller (1366×566: 376.6 versus 454.2 px). These are **different visual scales**. Other rotated azimuths and non-square boards need separate checks.

Changing reserve from 18% to 16% increases board height only from 50.9% to 53.7% (+5.5% relative) and reduces available edge pull. If the present input cap is left tied to reserve, D also *decreases* by 11.1%. At 1920×878, conservative R falls 177.2 → 161.1 px; at 1366×566, 114.2 → 103.8 px. Thus 16% alone misses both the +30% board-size aim and the 50 px 30%-power radius. Reducing fit reserve to zero raises board height to 74.5%, but leaves just 3.7% canvas-height minimum corner clearance; it is not an all-direction input solution.

At 30% power, linear 180 has radius 54 px and requires 270 px for 150%; linear 240 has radius 72 px and requires 360 px; quadratic 180 has radius 98.6 px and requires 220.5 px for 150%. All exceed conservative R even at 1920×878. Sampled piece *centers* at 1920×878 have 231 px clearance, so quadratic 180 might fit those centers in the current 18% pose, before piece hulls and red-dot/aim offsets. This is a research lead, not a pass. At 1366×566 sampled centers have only 148.9 px, excluding those three fixed-distance candidates in this pose. A viewport-scaled quadratic `D = min(preferred, R_min/√1.5)` is the mathematically consistent fixed scale across pieces/directions once true `R_min` is measured. With the conservative corner proxy it gives D=40.9/93.3/144.7 px and 30% radii 22.4/51.1/79.3 px across the three base canvases. It meets radius 50 at 1366 and 1920 **only at the current board scale** under this proxy, not at 800.

## Feasibility and next geometry measurement

No single tested reserve or fixed D satisfies +30% board height, 30% radius ≥50 px, and all-direction 150% reach across all three canvas sizes. The 800×248 case has a stronger vertical necessary condition: sampled rank 1–8 piece-center y coordinates span 103.0 px already, so even an ideal vertical recenter leaves at most `(248−103)/2 = 72.5` px all-direction pull from those centers. Quadratic radius 50 at 30% needs `D ≥ 50/√0.3 = 91.3`, hence 150% pull ≥111.8 px; linear needs D≥166.7 and 150% pull≥250 px. Enlarging the board increases that span. This proof is for these sampled centers in the current projection; it does not establish a universal impossibility across every camera angle, pitch, mode, or placement, and adding piece/aim bounds only tightens it.

The smallest **study candidate**, pending live geometry, is to keep the current 18% fit and measure actual selectable start-point clearance; if the desktop 1920×878 true minimum reaches 220.5 px, compare quadratic D=180 there. For 1366×566, compare a viewport-scaled quadratic using the measured true `R_min`, with a single D per canvas (no per-piece or per-direction changes). The 16% fit offers a modest visual increase but consumes pull clearance; use it only as an independent visual comparison. A +30% board height target means 66.2% of canvas height here, above the PRD's separate 55–65% candidate range, so decide which visual goal governs before acceptance. At 800×248, retain an explicit unresolved tradeoff or change the layout/camera/input contract with product approval; geometry cannot certify all three goals from these settings.

The front projection is vertically asymmetric: at 1920×878 the board AABB is y=253.6–700.8, leaving 253.6 px above and 177.2 px below. A screen-space upward shift of about 38 px would equalize board-corner clearance at this **same board scale**, potentially reclaiming lower empty space. It requires an off-axis projection or changed target/pose and must preserve the requested board-center zoom pivot and framing through rotation/resize. A plain target shift changes that pivot. Recentered clearance still does not establish 220.5 px for board corners or a 30% larger board. This possibility should be evaluated against HUD overlays and actual projected piece bounds, not assumed safe.

True `R_min` needs the projected world AABB or, preferably, screen-space extremal points of **every selectable piece mesh in its actual pose** plus its red-dot/aim start point (including transformed geometry and scale), for front, diagonal, and freely rotated camera angles. Include board corners separately for visibility, the effective release region (canvas and overlays/cancel dock), 100/150% piece caps, current mode, and all 8 pull directions. For each start point, compute ray-to-valid-release-edge and take the minimum across all points/directions. The current `scene.ts` board-corner fit ensures the board is visible; it does not establish that all selectable release vectors fit. The sample centers here omit piece hulls, occlusion, HUD hit regions and live gesture handling. No browser, live gameplay, user test, or network validation was performed.

`tutorial.ts` computes its guide from `computeEffectiveMaxDragPixels`, then caps a normal first-shot arrow at 64 px or 40% of D. Any curve change needs the same inverse mapping for guides and displayed percentages; the current visual arrow alone does not validate power reach.
