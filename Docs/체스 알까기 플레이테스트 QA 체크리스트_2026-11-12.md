기준 문서는 [플레이테스트 QA 및 개선 기획서 v1.1](체스%20알까기%20플레이테스트%20QA%20및%20개선%20기획서_2026-11-12.md)다. `PF-Rxx`는 요구사항이고 `PF-Txx`는 고정 사례 ID다. 최초 계획의 기대결과·상태는 아래 기준표에 보존하고, **이번 실행은 범위를 분리한 하위 사례와 실행 기록**에 추가했다. 부모 기준 전체를 통과로 옮기지 않는다. 당겨서 놓기는 사용자 검토 기준이며, 구체 거리·구도·문턱값의 체감 채택은 별도 비교 대상이다.

## 실행 조건

- 대상: itch 웹, 클래식·당구식, 마우스 우선. 공통 변경은 터치·일반 웹·CrazyGames·Android의 해당 경로를 회귀 확인한다.
- 조사 소스: `develop` HEAD `c82d1cd7e0c116598af7c134edaaa16f803b93d8` + 기존 작업 폴더. 실제 실행 전 빌드 번호와 dirty 여부를 새로 기록한다.
- 기본 viewport: 1366×768. 경계는 800×450 iframe·1280×720·1920×1080, 터치 회귀는 390×844. 확대 100/125/150%는 영향을 받는 입력·팝업 사례에 적용한다. CSS viewport와 DPR을 따로 기록한다.
- 환경 기록: 브라우저/OS/기기·입력·모드·언어·배율·프리셋·희망/실제 당김 거리·최소 유효 당김 공간·카메라 구도·배치·기물/강화·자세/타점·방향·계정 역할. 실기기·라이브 확인이 없으면 그 범위는 미확인으로 남긴다.
- 비교 데이터: 동일 초기 상태를 복원할 수 있는 로컬 QA 배치. 새 프로토타입·고정 파워 입력은 개발/QA용으로 표시하고 실제 플레이 결과와 구분한다.
- 온라인: 읽기와 게스트 시험을 포함해 실행 환경의 권한을 먼저 확인한다. 실제 랭크 점수·보상 변경은 해당 검증이 별도로 허용된 환경에서만 수행한다.
- 이번 실행: 로컬 자동 검사·브라우저 포인터/키보드·생성 itch 빌드 확인. 토너먼트·문장·새 능력 구현·공개 서버의 실제 랭크 경기는 범위 밖이다.

실행 우선순위 P1은 핵심 입력·저장/정산 위험, P2는 설명·발견성·실험을 뜻한다. 기획서 P0~P3의 개발 우선순위와 별개이며 결함 심각도가 아니다. 표의 구현 상태는 신규 요구 전체 기준으로 보수적으로 기록한다.

## 고위험 사례 상세

### PF-T01·02 선택과 발사

1. 정지한 폰·내 턴·카메라 고정 상태에서 press 위치와 모든 move/up 좌표를 CSS px로 기록한다.
2. 0변위, 1px 흔들림, 채택 문턱 직전/정확히/직후, 문턱 초과 후 작은 힘으로 복귀를 분리한다. 빠른 up과 마지막 좌표만 달라지는 경우도 포함한다.
3. 원시 입력→정규화 파워→큐 승인/거절→물리 적용→턴 변경을 같은 제스처 ID로 연결한다. 화면만 보고 작은 샷과 무효 입력을 혼동하지 않는다.
4. 승인 없는 입력은 실제 발사·턴 소비가 없고, 유효 입력은 1회인지 확인한다. 킹 특수 행동·버튼은 별도 상호작용으로 검사한다.

### PF-T04 가장자리

전체 교차 조합은 자동 입력 검사로 가능 범위를 계산하고, 실제 UI에서는 하단 전방·좌우 모서리·취소 영역 경계·150% 최악 조건을 우선 실행한다. `1.5 × D_effective ≤ R_min`을 실제 유효 영역 기준으로 확인한다. 캔버스 rect·기물/타점 투영 범위·HUD/취소 영역과 카메라 zoom·피치·지원 시점 범위를 기록한다. 누운 기물과 양 진영 시점을 포함하고, 유효 시작점에서 `R_min=0`이면 미해결로 판정한다. 정상 선택 가능한 말을 제외해 통과시키지 않는다. 조합 일부만 검사하면 검사한 조건을 적고 전체 조합 통과라고 쓰지 않는다. 경고 노출과 실제 파워 도달은 별개이며, 화면 밖 release·발사 버튼으로 우회한 결과는 통과가 아니다.

### PF-T05·08 감도와 손맛

동일한 입력 파워의 기대값을 먼저 고정하고 실제 발사 속도는 별도로 기록한다. 나이트 보정·강화·기물별 상한 때문에 같은 입력 파워의 물리 결과는 달라질 수 있다. 중앙과 가장자리의 같은 당김 거리는 같은 입력 파워여야 한다. 공간 확보를 위해 보드를 축소하거나 실제 거리를 줄였을 때 기물 식별·오선택·부분 파워 반복 성능이 나빠지는지도 함께 판정한다. 작은 화면에서 프리셋이 같은 실제값으로 제한되면 그 차이가 없다는 안내를 확인한다.

### PF-T15 온라인

게스트 친선전, 큐 등록/취소, 실제 로그인 계정의 전체 경기·정산을 각각 하위 결과로 기록한다. 모의 서버 검사는 프로토콜 범위만 증명한다. 상대가 없어 전체 경기를 못 했으면 시도한 단계와 차단 이유를 남기고 전체 사례는 통과시키지 않는다. 실제 정산 테스트가 허용되지 않으면 로컬 대역으로 임의 대체해 전체 통과를 주장하지 않는다.

## 새 실행 기록 형식

새 시도에는 다음 필드를 사례·시도별로 추가한다. 이번 실행은 아래 기록을 따른다.

`run_id / PF-Txx / 요구 v1.1 또는 개정판 / 실행자·시각 / 빌드·환경 / 준비 데이터 / 실제 행동·관찰 / passed|failed|blocked / evidence_kind(runtime|automated-test|code-review|supplied-report) / 증거 경로 / 남은 범위`

계획만 있는 경우 `actual_result=null`, `evidence_refs=[]`로 둔다. 수정 후에는 이전 실패를 보존하고 현재 적용을 `retest`로 바꾼 뒤 새 시도를 추가한다. 캡처만으로 실제 발사·네트워크·소리 검사를 통과시키지 않는다.

## 확인 수준과 다음 단계

원래 수용 묶음 **20개**를 보존하고, 현재 검증은 **통과한 하위 범위 17개·남은 하위 범위 8개**로 구분했다. 브라우저 assertion 233개나 자동 스크립트 수는 수용 사례 수와 다르다. 모든 요구 PF-R01~11에 연결 사례가 있으나 기획 전체 수용은 완료되지 않았다. 다음 우선 과제는 PF-T08-A 실제 조작 비교와 PF-T04-B의 시점/장치 확대다. 단순 문서 렌더링 검수는 게임 사례에 포함하지 않는다.

문턱값·R02 구도/실제 거리·기물 안내를 채택하거나 수정하면 기준 문서 버전을 함께 올리고 영향받는 사례만 갱신한다. 아직 승인되지 않은 후보값·장기 기능은 단독 출시 차단 사유로 확정하지 않는다.
