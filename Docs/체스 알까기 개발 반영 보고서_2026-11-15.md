# 체스 알까기 개발 반영 보고서

2026-11-15 · 대상 브랜치: develop · 기준 코드: f601434

이번 변경은 **실패해도 다시 배울 수 있는 플레이 흐름을 만들고, 위력을 낮췄을 때 생기는 이득과 손실을 실제로 비교한 작업**입니다. 1차 개선은 게임 코드에 반영했고, 2차 후보는 개발용 실험 도구로 준비했습니다. 공개 게임의 기본 위력·킹 승패 조건·카드 구조는 유지했습니다.

## 1. 무엇을 바꿨나요?

### 실패한 단계에서 다시 도전합니다

이전에는 패배가 도전 전체의 종료로 이어졌습니다. 이제 itch 일반 스테이지에서 지면 **현재 단계와 이번 도전에서 얻은 강화 카드를 유지한 채 같은 단계**를 다시 시작할 수 있습니다.

예를 들어 3단계에서 졌다면 1단계부터 카드를 다시 모으는 대신, 같은 강화를 가지고 3단계를 다시 풉니다. 말의 위치·자세·사용한 능력은 그 단계의 시작 상태로 돌아갑니다. 실패 직전의 불리한 보드를 그대로 이어받는 방식은 아닙니다.

무승부도 같은 단계에 다시 도전합니다. 기존의 “상대 기물을 모두 떨어뜨리면 승리”라는 규칙은 바꾸지 않았습니다.

### 메뉴 이동과 도전 종료를 구분합니다

메뉴로 나가는 것은 **잠시 멈추기**입니다. 단계를 이어서 할 수 있고, 그 행동만으로 보상을 지급하거나 강화 카드를 지우지 않습니다.

별도로 “도전 종료하고 정산”을 확인했을 때 이미 통과한 단계의 보상을 지급합니다. 새 도전을 시작하려고 해도 기존 도전의 종료가 먼저 확정되어야 합니다. 실수로 메뉴를 눌렀다는 이유로 진행을 잃지 않게 한 것입니다.

### 카드 선택과 보상을 중복 처리하지 않습니다

저장 지점을 **체크포인트**라고 합니다. 이번에는 단계 시작뿐 아니라 다음 상태도 구분해 저장합니다.

- 승리 후 제시된 카드와 아직 선택하지 않은 상태
- 선택을 확정하고 다음 보드를 준비하는 상태
- 도전을 종료하며 보상 지급을 확인하는 상태

따라서 새로고침해도 카드 선택지를 다시 뽑지 않습니다. 이미 선택한 카드로 다음 보드를 만들다가 실패하면 같은 선택으로 다시 준비합니다.

보상에는 도전마다 고유한 번호를 붙입니다. 같은 지급 요청이 다시 와도 **정산 영수증**을 확인해 이미 처리한 보상을 다시 더하지 않도록 했습니다. 여기서 영수증은 결제 영수증이 아니라 “이 도전의 보상을 처리했다”는 기록입니다.

### 저장 실패를 성공처럼 보여주지 않습니다

브라우저 저장이 실패해도 현재 창 안에서는 계속 플레이할 수 있습니다. 대신 창을 닫으면 미저장 진행을 잃을 수 있다고 안내합니다.

정산도 실제 저장·서버 확인이 끝나기 전에는 완료로 표시하지 않습니다. 같은 브라우저에서 같은 소유자의 itch 탭을 두 개 열었을 때는 한 탭만 진행하도록 보호했습니다.

### 결과를 관찰한 사실로 설명합니다

직전 샷에서 내 말과 상대 말이 실제로 몇 개 떨어졌는지 표시하고, AI가 쏜 샷이면 구분합니다. 그 샷의 증거가 없으면 원인을 추측하는 대신 남은 말 수를 보여줍니다. 새 문구는 기존 지원 언어 9개에 추가했습니다.

## 2. 2차 실험은 무엇을 비교했나요?

**실험 프로필**은 비교를 위해 값 하나를 달리한 설정 묶음입니다. 아래 후보들은 전용 개발 명령으로 실행할 때만 적용됩니다. 일반 빌드에 자동으로 적용되지 않습니다.

| 설정 | 바꾼 점 | 확인하려는 질문 |
|---|---|---|
| 현행 기준 | 기존 값 유지 | 비교의 출발점 |
| 지상 속도 9 / 8 | 기존 11에서 지상 기물의 초기 발사 속도 감소. 나이트 유지 | 적을 밀면서 내 말도 남기는 선택이 늘어나는가? |
| 폰 0.85 / 0.70 | 기준 속도에서 폰만 별도로 약화 | 폰의 효율을 낮춰도 접근·밀기·승격 역할이 남는가? |
| 룩 초과 위력 축소 | 100%를 넘는 위력 부분만 절반 | 강한 중앙 공격의 위험과 이득이 달라지는가? |
| 퀸 초과 위력 축소 | 퀸만 같은 방식으로 별도 비교 | 회전·강한 공격이 항상 유리한가? |
| 비숍 대각선 보너스 | 보드 대각선 ±12도에서 속도 10% 증가 | 방향 선택이 기물 역할을 구분하는 데 도움이 되는가? |

폰 약화와 전체 위력 감소를 동시에 섞어 결과의 원인을 흐리지 않았습니다. 킹은 기존 교대·방어를 확인했고, 킹을 떨어뜨리면 즉시 패배하는 새 규칙은 만들지 않았습니다. 카드 유지·삭제 비교도 이번 범위에서 제외했습니다.

반발·감쇠 조정은 원인이 확인될 때만 하기로 했습니다. 이번 분산 배치에서는 적 3개 이상을 한 번에 떨어뜨리는 과잉 연쇄를 재현하지 못해 이 계수는 바꾸지 않았습니다. 적이 모여 있을 때 가능한 의도적인 연쇄 공격도 보존했습니다.

## 3. 실제 측정 결과는 어땠나요?

중앙·네 가장자리·가까운/먼 적·군집/분산·아군 방해·벽·구멍·누운 말의 **13개 고정 배치**, 기물 6종, 설정 8개를 사용했습니다. 같은 조건을 다시 만들고 실제 게임의 물리 계산으로 샷 **2,470회**를 실행했습니다.

그중 2,080회는 설정별 비교이고, 390회는 같은 입력 반복 및 각도 ±1도·파워 ±1%포인트 차이를 비교한 것입니다.

아래의 “중간 세기 안전 성공”은 30% 또는 60% 샷에서 **상대 말을 하나 이상 떨어뜨리고 발사한 내 말은 남은 경우**입니다. 움직임을 강제로 끝낸 경우는 이 성공 수에 포함하지 않았습니다. 각 설정의 중간 세기 표본은 156회입니다.

| 설정 | 중간 세기 안전 성공 | 함께 확인한 비용 |
|---|---:|---|
| 현행 | 12건 | 비교 기준 |
| 지상 9 | 16건 | 일부 배치의 직접 접촉 감소, 강제 정착 증가 |
| 지상 8 | 23건 | 일부 배치의 직접 접촉 감소 |
| 폰 0.85 | 13건 | 이득이 작고 강제 정착 증가 |
| 폰 0.70 | 14건 | 일부 배치의 직접 접촉 감소 |
| 룩 초과분 축소 | 12건 | 중간 세기의 성공 수 변화 없음 |
| 퀸 초과분 축소 | 12건 | 중간 세기의 성공 수 변화 없음 |
| 비숍 대각선 | 11건 | 이 표본의 안전 성공 감소 |

**속도 8은 추가 검수할 가치가 있지만 바로 채택하지 않았습니다.** 상대를 밀고 내가 살아남는 경우는 늘었지만, 시험한 세기에서는 아군이 막는 폰 배치와 구멍이 있는 퀸 배치의 직접 접촉을 잃었습니다. 힘을 낮추면 제어가 쉬워지는 대신 적에게 닿지 못하는 상황도 생길 수 있기 때문입니다.

이것은 고정 샷 표본의 횟수이며 사람의 승률이나 재미 점수가 아닙니다. 모든 연속 세기와 조준 각도를 탐색한 것도 아니므로, 해당 공격이 완전히 불가능하다고 단정하지 않았습니다.

## 4. 직접 조작 QA에서는 무엇을 확인했나요?

Orca의 ChessAlkkkaegi 프로젝트 QA 작업트리에 app-qa-human 검증을 요청했고, 별도 QA 보고서를 확인했습니다.

QA에서는 격리된 로컬 게스트로 **실제 플레이어 발사 47회**를 확인했습니다. 기준 → 속도 8 → 기준 → 속도 9의 순서로 다시 비교하고, 폰 약화·룩/퀸의 중앙 및 회전 타점·비숍 대각선·나이트·킹 능력과 재도전도 조작했습니다.

실제 입력에서도 위력 차이는 나타났습니다. 다만 같은 정면 배치에서는 속도를 낮춰도 내 말과 상대 말이 함께 떨어지는 결과가 유지됐습니다. 퀸의 강한 공격을 줄였을 때 오히려 퀸이 살아남지 못한 표본도 있었습니다. **“속도가 낮으면 언제나 더 안전하다”는 결론은 맞지 않았습니다.**

이번 QA는 사전 설명을 받은 AI의 직접 조작 검사입니다. 실제 사람 여러 명의 선호나 재미 연구를 대신하지 않습니다.

### 남아 있는 화면 문제

| 문제 | 관찰한 영향 | 현재 회복 방법 |
|---|---|---|
| 세로 → 가로 전환 후 보드가 작게 남음 | 말을 선택할 화면 영역이 작아짐 | 메뉴에서 재개하면 프레이밍 회복 |
| 시작 설명 팁이 상단 목표를 덮음 | 팁이 있는 동안 목표와 남은 적 수를 읽기 어려움 | 팁의 닫기 버튼 사용 |
| 당구 조준의 취소·고도 표시가 겹침 | 두 문구가 겹쳐 읽기 어려움 | Escape로 조준 취소 가능 |

기준과 관련 후보에서 관찰된 문제이며 이번 위력 실험만의 회귀라고 확정하지 않았습니다. QA 범위에서 게임 진행을 막는 Major/Critical 문제는 확인하지 않았지만, 위 화면 문제를 해결했다고 처리하지도 않았습니다.

## 5. 어떤 검증을 했고 무엇이 남았나요?

자동 검사로 재도전 상태 전이, 카드 중복 선택 방지, 저장 실패, 정산 요청 재전송, 계정 변경, 기존 저장 이행을 확인했습니다. 계정 정산용 SQL도 로컬 PostgreSQL 모형인 PGlite에서 검사했습니다.

2차 실험에서는 실제 초기 발사 속도와 계산값, 비숍 대각선 경계, 다른 모드의 값, 나이트의 최소 도약·각도와 고정 배치 최종 자세 보존을 확인했습니다. 킹 교대·방어의 사용권, 킹 단독 발사, 편심 회전, 질량만 늘렸을 때 속도와 충격량의 차이도 검사했습니다.

**로그인 정산용 DB 변경은 파일 작성과 로컬 검사까지만 끝났습니다.** 실제 Supabase 적용과 실제 계정 지급·재접속 검수는 남아 있습니다. 서버 기능이 없으면 지급 완료를 꾸미지 않고 정산 대기로 남습니다. 다른 언어의 전체 화면, 실제 모바일·터치, 모든 카드/연구 조합, 승격 완료와 반격 생존도 전부 검증한 것은 아닙니다.

새 SQL 검사는 기존 로컬 도구인 .orca/sql-check의 PGlite가 준비된 환경에서 실행했습니다. 일반 웹 실행에 필요한 의존성은 추가하지 않았습니다.

푸시 직전에는 check:solo-retry, check:strategy-experiments, 정산 SQL 검사와 itch 빌드를 다시 실행해 통과를 확인했습니다. 실험 검사 묶음은 2,470회 측정부터 후속 검사까지 다시 실행했습니다. 기존 일반 회귀 묶음·웹 빌드·오류 복구 브라우저 검사는 앞선 구현 단계에서 통과했으며, 이번 재검사와 구분합니다.

## 6. develop에 무엇을 올리나요?

이번 커밋에는 1차 게임 코드·저장/정산 SQL·전용 검사, 2차 개발 실험 도구, 관련 기획/QA 문서와 이 보고서를 포함합니다. 기존 스토어 설명 수정과 별도 퍼즐 검사 결과는 이번 변경에 섞지 않습니다.

develop은 변경을 모아 검토하는 개발 브랜치입니다. **develop에 코드를 올리는 것과 공개 게임에 배포하는 것은 다른 단계**입니다. 현재 GitHub Pages 워크플로는 main을 대상으로 하며, 이번 작업은 main·itch 업로드·운영 DB 적용을 실행하지 않습니다.
