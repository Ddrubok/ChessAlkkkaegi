# 계정 진행도 적용 안내

## 적용 순서

1. Supabase 프로젝트의 **SQL Editor → New query**를 엽니다.
2. [20260915_account_progress.sql](migrations/20260915_account_progress.sql) 전체를 붙여 넣고 실행합니다.
3. `account_progress_applied` 결과를 확인합니다. 같은 SQL은 다시 실행해도 됩니다.
4. 그 다음 새 웹 버전을 배포하고, Android는 웹 빌드 → `npx cap sync android` → AAB/APK 재빌드 순서로 반영합니다.

SQL 적용 전에 새 클라이언트를 배포하면 계정 진행도 조회가 실패하여 플레이가 잠깁니다. 배포할 프로젝트에서 완료 마커를 먼저 확인하세요.

## 저장하는 내용

- 최대 클리어 스테이지, 연구 포인트, 기물 연구 상태
- 기초·심화 튜토리얼 완료 여부 (`true`만 완료)
- 퍼즐 클리어 목록과 메달
- 실제 퍼즐 플레이의 상세 기록 `ca_puzzle_progress_v1` (최고 메달, 해금 등에 사용)

등록 계정은 `auth.users.id`별 `public.account_progress` 한 행에 저장합니다. 게스트는 기존 기기 저장을 사용합니다. 로그인 시 서버 기록을 먼저 불러옵니다.

로그인하면 서버 계정 기록을 자동으로 불러오며, 플레이 중 변경사항은 자동 저장합니다. 서버 기록이 없는 계정은 기본 진행도로 시작합니다. 기기의 기존 게스트 기록은 계정으로 섞지 않고 그대로 보존합니다. 수동 가져오기·새로 시작 버튼은 표시하지 않습니다.

계정별 임시 캐시 `ca_account_progress_v1:<사용자 UUID>`에는 저장 대기 데이터를 보관합니다. 일시적인 서버 저장 실패는 10초 간격으로 최대 3회 자동 재시도하며 오류가 있을 때만 재시도 버튼을 표시합니다. 연결이 복구되거나, 같은 계정으로 다시 로그인하면 저장을 재시도합니다. 이 캐시는 서버 저장 완료 전까지 삭제하지 마세요.

다른 기기가 먼저 저장하여 버전이 달라졌다면 자동 덮어쓰지 않습니다. **기기 기록 백업 후 서버 기록 사용**을 선택하면 충돌 기록을 `<캐시 키>:backup:<시간>`에 보관하고 서버 기록을 불러옵니다. 연구 포인트와 연구 상태는 함께 저장하므로 임의로 두 기기의 포인트를 합산하지 않습니다.

## 서버 접근과 검증

- RLS: 본인의 행만 조회. 익명 사용자는 접근 불가.
- 클라이언트의 직접 INSERT/UPDATE/DELETE 권한 없음.
- `get_account_progress(p_expected_user_id uuid)` → `{data, revision}`. 새 계정은 `{data:{}, revision:0}`.
- `save_account_progress(p_data jsonb, p_expected_revision bigint, p_expected_user_id uuid)` → 저장된 `{data, revision}`.
- 실제 소유자는 항상 `auth.uid()`로 결정합니다. `p_expected_user_id`는 계정 전환 중 지연 요청을 거절하기 위한 일치 확인용입니다.
- 버전 불일치는 `40001`, 계정 불일치·미인증·익명 요청은 `42501`로 거절합니다.
- 허용된 8개 키, 문자열 값, 숫자 범위, JSON 형식, 256KB 크기를 검사합니다. 포인트·연구 상태는 함께 존재해야 합니다.
- Auth 계정 삭제 시 해당 진행도는 외래 키 CASCADE로 삭제됩니다. 브라우저 데이터 삭제만으로 서버 기록은 삭제되지 않습니다.

싱글 플레이 진행도는 클라이언트가 계산합니다. 계정 격리와 덮어쓰기 방지가 적용되지만, 클리어·포인트 획득 자체를 서버에서 검증하는 부정행위 방지 시스템은 아닙니다. 온라인 MMR 정산과 별개입니다.

## 코인 제거

온라인 매칭의 잔액 검사·차감, 코인 HUD·충전소·자동 충전·광고 보상·친구 초대 코인 지급을 제거했습니다. 연구 포인트는 유지합니다. AdMob/AdSense 공통 연동은 유지하되 코인을 받는 보상 광고 진입점은 없습니다.

기존 `ca_unified_energy_v1` 로컬 값은 더 이상 읽거나 쓰지 않습니다. 이전 추천인 SQL을 다시 실행할 필요가 없으며, 과거 서버 추천 이력은 이 변경으로 삭제하지 않습니다.

## 확인 방법

- `cd web` 후 `npm run check:progress`, `npm run check:ads`, `npm run check:regressions`, `npm run build`.
- 로그인 A에서 진행 후 서버 저장 완료 확인 → 다른 브라우저에서 A로 로그인하여 같은 기록 확인.
- 로그아웃 후 B로 로그인하여 A의 기록이 보이지 않는지 확인.
- 서버 조회 실패 시 빈 진행도가 서버로 전송되지 않고 재시도 안내가 표시되는지 확인.
- 두 기기에서 같은 계정을 수정하면 늦은 저장이 충돌 안내로 바뀌는지 확인.
- 코인이 0이던 기기에서도 온라인 매칭을 시작할 수 있는지 확인.

RLS를 점검할 때 SQL Editor의 기본 관리자 역할로 조회하면 RLS를 우회합니다. 실제 로그인 계정의 클라이언트 또는 JWT와 역할을 지정한 격리 테스트를 사용하세요.
