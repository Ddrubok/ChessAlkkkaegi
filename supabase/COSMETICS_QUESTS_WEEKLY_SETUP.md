# 배너 꾸미기·퀘스트·주간 챌린지 SQL 적용

세 기능을 **같은 Supabase 프로젝트에, 파일별로 나누어** 적용합니다. 한 파일이 성공한 것을 확인한 뒤 다음 파일을 실행하세요. 세 SQL은 각각 트랜잭션으로 실행되며 재실행할 수 있습니다.

이번 준비 작업에서는 운영 DB에 접속하거나 적용하지 않았습니다. 보상·게임머니·연구 포인트를 지급하는 작업도 포함하지 않습니다.

## 1. 시작 전 확인

1. 실제 게임에서 사용하는 Supabase 프로젝트를 선택합니다.
2. 왼쪽 **SQL Editor → New query**를 엽니다. Table Editor에서 테이블을 직접 만들 필요는 없습니다.
3. [사전 확인 SQL](./preflight_cosmetics_quests_weekly.sql)의 내용을 전부 붙여넣고 **Run**을 누릅니다.
4. `release_prerequisites_ready`이면 다음 단계로 진행합니다. `release_prerequisites_missing`이면 결과의 `false` 항목부터 확인합니다.

이 확인은 기존 계정 진행도·배너 v3·확정 대전 결과 테이블과 DB 기본 함수가 있는지 검사합니다. 기존 마이그레이션을 무조건 다시 실행하거나 테이블을 지우지 않습니다.

## 2. 순서대로 세 파일 실행

각 파일마다 새 쿼리를 열고 **파일 전체**를 붙여넣습니다. 함수 이름만 실행하는 것이 아닙니다.

| 순서 | 파일 | 성공 표시 |
| --- | --- | --- |
| 1 | [배너 꾸미기](./migrations/20260918_profile_cosmetics.sql) | `profile_cosmetics_migration_applied` |
| 2 | [일일·주간 퀘스트](./migrations/20260918_quest_mvp.sql) | `quest_mvp_applied` |
| 3 | [주간 챌린지](./migrations/20260919_weekly_challenge_mvp.sql) | `weekly_challenge_mvp_applied` |

**주간 챌린지는 이 폴더의 수정된 파일을 사용하세요.** GitHub에서 가져온 원본에는 `pg_catalog.coalesce` 때문에 로그인 RPC가 실패하는 문제가 있어 `coalesce`로 수정했습니다. 이미 원본을 적용했다면 수정본 전체를 다시 실행합니다.

주차가 끝난 도전의 제어 요청에는 오래된 수정 번호 오류보다 `WEEK_EXPIRED`를 먼저 반환하도록 수정했습니다. 만료가 원인임을 앱에서 정확히 구분하기 위한 변경입니다.

오류가 나면 다음 단계로 넘어가지 말고 오류 메시지를 보관합니다. 해당 쿼리의 트랜잭션이 취소되므로, 수정 후 해당 파일을 다시 실행하면 됩니다. 이미 성공한 앞 단계는 유지됩니다.

## 3. 설치 상태 확인

[통합 확인 SQL](./verify_cosmetics_quests_weekly.sql)을 실행합니다.

`cosmetics_quests_weekly_ready`와 모든 항목 `true`가 나오면 9개 공개 RPC의 존재·로그인 권한·안전한 함수 검색 경로 및 퀘스트/챌린지 테이블의 접근 제한이 준비된 상태입니다. 이 쿼리는 플레이어 진행도를 읽거나 바꾸지 않으며 PostgREST에 새 RPC 목록을 갱신하도록 알립니다.

이 표시는 **설치 확인**입니다. 실제 로그인한 앱에서 저장·동기화되는지 확인하는 단계까지 대신하지 않습니다. SQL Editor에서 `auth.uid()`는 보통 비어 있으므로 로그인 전용 RPC를 그냥 호출하면 권한 오류가 나는 것이 정상입니다. 테스트를 위해 로그인 검증을 제거하지 마세요.

## 4. 실제 앱 확인

현재 로컬에는 배너 변경을 보존하면서 두 SQL만 GitHub `origin/main`에서 가져왔습니다. 최신 퀘스트·챌린지 웹 코드를 이 작업 폴더에 병합하거나 배포한 상태는 아닙니다. 해당 기능이 들어간 웹/앱 버전에서 아래 항목을 확인해야 합니다.

- **배너:** 회원 계정에서 6개 항목 적용 → 새로고침 → 같은 계정의 다른 기기에서 장착 상태 확인.
- **퀘스트:** 퀘스트 화면에서 `get_quest_snapshot_v1` 성공 → 정상 플레이 후 `submit_quest_events_v1` 성공 → 같은 요청 재전송 시 중복 증가가 없는지 확인.
- **PVP 승리:** `match_settlements`에 해당 계정의 확정 승리(`settled_at`, `winner_id`, 참가자 ID)가 기록된 뒤에만 퀘스트 반영. 아직 확정되지 않은 결과나 다른 계정의 승리는 거부되어야 합니다.
- **주간 챌린지:** `get_weekly_challenge_snapshot_v1` 조회 → `begin_weekly_challenge_attempt_v1` 시작 → `append_weekly_challenge_attempt_events_v1`로 진행 저장 → `control_weekly_challenge_attempt_v1`의 재개(`resume`)·다른 기기 인계(`takeover`)·종료(`terminate`) 확인.
- **재개 제한:** 진행 중인 물리 시뮬레이션을 그대로 복구하는 기능은 아닙니다. 재개·인계는 `ready-for-stage` 또는 `awaiting-card` 상태에서 허용됩니다. 플레이 도중에는 복구/인계 제한 응답이 정상일 수 있습니다.
- **계정 분리:** A 계정 기록이 B 계정이나 게스트에게 나타나지 않아야 합니다. 두 기기에서 같은 계정으로 조회하면 서버 저장 결과가 같아야 합니다.

## 5. 갱신 시각과 보상 범위

일일 퀘스트는 **매일 오전 5시 KST**, 주간 퀘스트와 주간 챌린지는 **월요일 오전 5시 KST** 기준입니다. 서버 시각으로 기간을 계산하고 조회/요청 때 현재 기간을 생성·전환하므로 별도 예약 작업(cron)을 등록할 필요가 없습니다. 실제 시각이 지난 뒤 앱을 다시 조회하여 새 기간이 나오는지 확인합니다.

이번 SQL은 진행도·도전·기록을 저장합니다. 퀘스트 보상·게임머니·연구 포인트 지급은 추가하지 않습니다. 기존 PVP 정산 기능 자체의 MMR 처리도 이번 적용으로 바꾸지 않습니다.

## 6. 적용 전에 수행한 로컬 검증

별도의 로컬 PostgreSQL 호환 실행 환경(PGlite)과 테스트 계정을 사용했습니다. 운영 Supabase의 실제 계정이나 기록으로 시험한 것은 아닙니다.

- 세 기능을 같은 DB에 설치하고 각 SQL을 반복 실행: 통과.
- 통합 확인 SQL의 9개 RPC 및 7개 테이블 검사: 통과.
- 퀘스트: KST 갱신 경계, 로그인/계정 분리, 확정 승리 승인과 가짜·미확정 승리 거부, 중복 이벤트, 일반 진행도 증가: 통과.
- 주간 챌린지: 13개 시나리오(시작·재개·기기 세션 인계·종료·액션 저장·카드 선택·10스테이지 종료·최고 기록 보존·만료 등): 통과.
- 배너: v4 저장과 이전 버전 저장 호환: 통과.

두 기기의 세션 ID와 중복 요청은 로컬 DB에서 검증했습니다. 실제 앱 두 대를 사용한 운영 동기화 확인은 4단계에서 수행합니다.
