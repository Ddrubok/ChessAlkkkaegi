# 온라인 대전(PVP) 설계 (2026-07-26)

## 1. 개발자 확정 사항

1. **연결 방식 = P2P** (브라우저끼리 직통). 서버를 두지 않는다. GitHub Pages 배포 구조를 바꾸지 않는다.
2. **매칭 = 방 코드** (친구끼리). 랜덤 매칭은 이번 범위 밖.
3. **순서 = P1부터 계획대로 자동 진행** (개발자 부재 중 설계자 판단으로 진행, 가정은 §3에 기록).

## 2. P0 실측 결과 (설계의 토대)

`determinism-probe`로 발사 10개·9,000스텝 시나리오를 Node와 브라우저에서 각각 돌린 결과
**10개 체크포인트의 SHA-256이 전부 일치**했다(64비트 실수 원본 비트 기준). Node 2회 실행도 파일 해시 동일.

따라서 온라인 동기화는 **입력 전송 방식**을 채택한다.

- 한 턴에 보내는 것: `말 id + 방향(x,y,z) + 세기 + 적용점(x,y,z) + 속도배수` ≈ 30바이트
- 받은 쪽은 같은 발사 경로로 재생 → 양쪽이 같은 결과
- **상대 샷은 기존 AI 조준 연출(R33)을 그대로 재사용해 실시간으로 보여준다**
- 턴 끝에 상태 해시를 교환해 어긋남을 감지한다(보험). 어긋나면 그때만 스냅샷으로 복구

미검증: 다른 물리 기계 간 결정성. 프로브를 배포판에 올리고 동료에게 `?probe=1` 링크를 보내 해시를 대조하면 종결된다.

## 3. 설계자 가정 (개발자 부재 중 결정 — 복귀 후 확인 대상)

- **시그널링(처음 서로를 찾는 절차)은 서버 없이 수동 코드 교환으로 한다.**
  WebRTC는 연결 전에 양쪽이 접속 정보를 주고받아야 하는데, 서버를 두지 않기로 했으므로
  그 정보를 **압축한 초대 코드 문자열**로 만들어 사람이 복사해 전달한다.
  절차: 방장이 "방 만들기" → 초대 코드 생성·복사 → 카톡 등으로 전달 → 상대가 붙여넣고 "참가"
  → 응답 코드 생성 → 방장에게 전달 → 방장이 붙여넣으면 연결 완료.
  왕복 두 번이 필요한 것은 서버 없는 P2P의 구조적 한계다.
  코드는 접속 정보에서 불필요한 줄을 걷어내고 브라우저 내장 압축으로 줄인다.
  **대안(후속)**: 공개 시그널링 서버를 쓰면 6자리 방 번호가 되지만 외부 서비스 의존이 생긴다.
- **진영**: 방장이 백(선공), 참가자가 흑.
- **모드**: 온라인은 2인 대전 규칙만 사용한다(스테이지 버프·카드·영구 강화 없음). 공정성 때문.
- **카메라**: 2인 대전과 동일한 턴 회전을 쓰되, **각자 자기 진영이 화면 아래에 오도록** 본다.
  즉 회전 목표 방위는 "현재 턴"이 아니라 "나의 진영" 기준이다.
- **어긋남 감지**: 턴 정착 후 말 32개의 위치·회전 해시를 서로 보낸다. 불일치 시 백(방장) 상태를 정답으로 삼아 스냅샷 복구.
- **끊김**: 상대 연결이 끊기면 재연결 대기 화면을 띄운다.
- **끊김 종료의 승패 처리 (2026-07-27 개발자 확정, 기존 "기권 처리" 폐기)**:
  재개를 포기하고 끝낼 때는 **승패를 남기지 않고 무효 종료**한다. 문구는 "상대와 연결이 끊겨 대국이 종료되었습니다",
  버튼은 `메뉴로`만. 버튼 이름도 `대국 포기` → **`대국 종료`**로 바꾼다.
  근거: 서버 심판이 없어 누가 먼저 이탈했는지 판정할 수 없다. 남은 쪽을 패배로 두면 억울하고,
  승리로 두면 인터넷이 끊긴 경우까지 상대 승리가 되며 불리할 때 창을 닫는 행위가 이득이 된다.
  전적을 기록하지 않는 현 단계에서는 무효가 가장 정직하다.
  **랭킹·서버 심판이 도입되면 "남은 쪽 승리"로 전환하는 것을 후속 과제로 둔다.**
  단, 플레이어가 명시적으로 누르는 **기권(`기권` 버튼)은 그대로 기권자 패배**로 유지한다 — 이건 본인 의사다.
- **P4 재접속 권한**: 재연결은 기존 채널을 되살리지 않고 새 WebRTC 초대·응답 코드를 교환한다.
  양쪽 턴 번호와 상태 해시가 같으면 즉시 재개한다. 다르면 방장(백)의 전체 입력 기록과 현재 상태가 정답이다.
  참가자가 뒤처졌으면 방장 기록 꼬리를 받은 뒤 방장 상태로 맞추며, 참가자가 방장보다 앞서 있어도
  참가자의 추가 진행을 버리고 방장 턴으로 되감는다. 서버 심판이 없는 친구 대전에서 권위가 갈리는 것을 막기 위한 규칙이다.
- **P4 창 종료 뒤 새 참가자 재접속 (2026-07-27 실사용 결함 수정)**:
  최초 연결 때 매치 ID를 만들고 초대·응답·재개 메시지에 계속 싣는다. 참가자 창이 완전히 닫혀 기록이 0턴인
  새 런타임으로 참가해도 같은 매치 ID의 재접속 코드라면 새 대국을 시작하지 않는다. 방장이 전체 입력 기록과
  현재 권위 스냅샷을 보내고, 참가자는 이를 모두 받은 뒤 같은 턴·진영에서 입력을 연다.
  로컬 저장은 필수 경로로 두지 않는다. 새 창에는 방장이 발급한 코드 자체가 매치 ID와 재접속 의도를 담고 있고,
  서버 없는 구조에서 복구 정답은 어차피 살아 있는 방장뿐이다. 오래된 로컬 기록을 후보로 자동 채택하면 오히려
  폐기된 대국과 섞일 위험이 있어, 이번 범위에서는 방장 전체 전송을 단일 복구 경로로 유지한다.
  위치·회전 스냅샷만 적용하면 좌표·속도·수면 수와 스텝 수가 같아도 Rapier의 접촉·솔버 내부 이력은 같지 않다.
  브라우저에서 재합류 직후 원시 좌표가 비트 단위로 같지만 다음 충돌 해시가 갈리는 것을 확인했으므로, 새 참가자는
  표준 시작 월드에서 방장 입력 기록을 실제 발사·고정 스텝 경로로 모두 재생한다. 재생 해시가 방장 권위 해시와
  일치하면 스냅샷은 적용하지 않아 내부 이력을 보존하고, 불일치할 때만 권위 스냅샷을 최종 안전망으로 사용한다.
- **부정행위**: 친구 간 대전 전제이므로 방어하지 않는다. 랜덤 매칭 도입 시 서버 심판이 필요하다.

| **P3** | 턴 교환 + 상대 샷 연출 + 어긋남 감지 | ✅ 완료·게이트2 통과 |

P1은 온라인의 토대이면서 동시에 **리플레이 기능**을 만든다.

### P4 게이트2 실측값 (2026-07-27, 설계자 직접 측정)

셀프테스트(실제 WebRTC 루프백 + 실제 두 물리 월드), 전 과정 console.error·window error **0건**.

| 시나리오 | 결과 |
|---|---|
| 창 종료 뒤 새 참가자 재합류(2턴 시점) | 재생 일치, 후속 4수 desync 0, 전송 6,658바이트 |
| 창 종료 뒤 새 참가자 재합류(6턴 시점) | 재생 일치, 후속 4수 desync 0, 전송 7,756바이트 |
| 진짜 한 턴 뒤처짐 복구(4턴 시점) | 재생 일치, 후속 4수 desync 0, 전송 6,387바이트 |
| 살아 있는 링크 재연결 / 양 진영 기권 | 통과 |

두 창(같은 원본의 독립 인스턴스 2개) UI 게이트 — 초대 644~650자·응답 590~594자로 실제 연결,
끊김 종료 문구·버튼·승패 없음 일치, 명시적 기권은 기권자 `패배`·상대 `승리`.

**미검증 1건**: 몇 수를 둔 뒤 창을 닫고 **메뉴 UI로** 재합류하는 경로. 화면에서 수를 두려면 3D 캔버스
좌표 조준이 필요해 자동화하지 못했다. 0턴 상태로는 새 대국과 이어받은 대국이 구분되지 않아 검증 가치가 없다.
같은 경로의 런타임 동작은 셀프테스트(2턴·6턴)와 `online-check [통과 i/j]`가 덮는다.
닫으려면 개발용 질의 플래그로 "현재 차례에 정해진 한 수를 쏘는" 훅이 필요하다 — 개발자 결정 사항.

### 이번 라운드에 잡은 결함 3건 (헤드리스 검사가 놓치던 것)

1. 새 참가자 복구가 월드를 **재생하지 않고 스냅샷으로 놓아서**, 재합류 후 매 턴 스냅샷 복구가 돌았다.
   `[통과 j]`가 "해시가 결국 같아지는지"만 봐서 복구가 만든 일치를 정상으로 판정했다.
2. `makeGuestOneTurnBehind` 훅이 참가자를 스냅샷으로 되감아, 직전 라운드의 "뒤처짐 복구 검증됨"이
   실제 경로를 한 번도 밟지 않은 채 통과하고 있었다.
3. 대국 종료 뒤에도 `기권`이 살아 있어, 승패 없이 끝낸 무효 종료를 `패배`로 덮어쓸 수 있었다.

교훈: **검사는 "결과가 같아졌는가"가 아니라 "복구가 몇 번 돌았는가"까지 봐야 한다.** 그리고 테스트 훅이
제품 경로를 우회하면 통과는 아무 의미가 없다.

### P1·P2 실측값 (게이트2에서 설계자가 직접 확인)

- 한 턴 전송량 **197바이트**. 예시:
  `[턴번호, 진영, "white-bishop-c1", 방향xyz, 세기, 적용점xyz, 속도배수, 상태해시]`
- 기록→재생 해시 일치: 핫시트 10/10, 스테이지(카드+영구강화 적용) 10/10. 세기 변조는 해당 턴에서 정확히 검출.
- 초대 코드 **595자**, 응답 코드 **555자** (SDP 축약 + deflate + base64url). 카톡 한 메시지로 전달 가능한 길이.
- 브라우저 안에서 호스트·게스트 두 링크를 붙여 실제 연결 성공:
  `idle → waiting-answer → connecting → connected`, 턴 페이로드 왕복 무결성 일치, 32말 스냅샷(1,807바이트) 전송 정상.
- 끊김 감지 동작 확인. 단, **정상 종료는 `disconnected`, 급단절은 `failed`로 갈린다** — P4에서 두 경우를 같은 화면 흐름으로 묶을 것.
- STUN(stun.l.google.com)은 주소 반사만 하는 무상태 서비스라 "서버를 두지 않는다"는 결정에 어긋나지 않는다.

## 5. 검증 방침

- 각 슬라이스: tsc + 빌드 + 기존 W1~W5 회귀 + 슬라이스 전용 헤드리스 검증.
- 연결 계층은 브라우저 두 개(같은 기계, 다른 탭/창)로 실제 연결해 게이트2.
- 커밋하지 않는다. 개발자 복귀 후 슬라이스별 커밋 제안 일괄 전달.
