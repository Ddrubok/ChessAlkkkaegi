## 0. 확정된 프로젝트 방향 (변경 불가 전제)

- **룰**: 순수 알까기. 체스 이동 규칙 없음, 말 모양·시작 배치만 체스. 승리 = 상대 말 전부 판 밖 낙하.
  **넘어짐 허용** — 말이 넘어져도 죽지 않고, 누운 상태 그대로 다시 튕길 수 있다. 아웃 판정은 오직 "판 밖 낙하".
- **기술**: Three.js + Rapier(@dimforge/rapier3d-compat) + Vite + TypeScript. 3D, 실제 물리(말 형상 기반 convex hull, 종류별 무게).
- **조작**: 당구식(각도 조준 + 세기). 데스크톱 마우스 + 터치 병행. (조작은 슬라이스 2 — 본 문서 범위 아님)
- **순서**: 핫시트 → AI 대전 → GitHub Pages 배포 → 온라인(추후).
- **저장소 (2026-07-25 개발자 결정)**: 웹 버전은 동료의 기존 저장소 `ChessAlkkkaegi`(GitHub `Ddrubok/ChessAlkkkaegi`) **안에** 둔다.
  레포 루트 = `resource/`(공용 원본 에셋) + `unity/`(동료 Unity 버전) + `web/`(웹 버전) 3형제 구성.
  GitHub Pages도 이 저장소에서 설정한다. 웹 전용 별도 레포는 만들지 않는다.
- **금지**: `unity/`와 `resource/` 아래는 **읽기 전용** — 동료 작업물이므로 수정 금지. 원본 `chess.fbx`도 읽기만 한다.
  Unity/Unity MCP는 이 프로젝트와 무관.
  원본 무변경 검증 SHA-256: `EC72D21CF6ACE76BFBC6F40DB7EF8DA6DB7C5B24D0098ADA4CD9438449870CF0`

## 1. 에셋 실측 (게이트1 리뷰 Codex 월드 변환 대조로 정정 완료)

원본 에셋 = 레포 루트의 `resource/chess.fbx` (웹 프로젝트 기준 `../resource/chess.fbx`) — 바이너리 FBX v7300, 38.4MB, Maya 익스포트. Texture/Video 객체 없음.

- 지오메트리 34개 = **보드 2개**(`pPlane1` 플레이 면 약 23.65×23.65 + `polySurface51` 프레임 약 29.11×29.11, 두께 약 0.876) + **말 32개**(시작 배치 완전체).
- 셀 크기 ≈ 2.956 (플레이 면 23.65 / 8).
- 이름은 신뢰 불가: `King` Null은 메시 자손 없음. `Bishop*`만 유효.
- 좌표는 Model transform이 아니라 **`scene.updateMatrixWorld(true)` 후 `Box3.setFromObject(mesh)` 월드 AABB 중심** 기준으로만 판단 (계층에 피벗·회전·스케일·bake 혼재).
- 고폴리 주의: 대표 6종+보드 삼각화 시 약 106만 출력 정점(위치+노멀 약 24.4MiB) → **감축 없이는 웹 배포 불가**.

### 참고 실측표 — **코드에 하드코딩 금지**

FBX 원본의 control point 수와, FBXLoader가 삼각화·비인덱스 전개한 뒤 `position.count`로 관측되는 값은 서로 다르다.
아래 표는 **변환 보고서를 사람이 대조하기 위한 참고값**일 뿐이며, 판별 로직은 이 숫자에 의존하지 않는다(§2 자기 보정 방식).

`position.count` 열은 **three.js 0.185.1 FBXLoader로 실제 관측한 값**(2026-07-25 브라우저 변환 실행 + 리뷰 Codex 독립 파싱, 두 경로 일치).
control point에서 산술로 추정한 삼각형 수보다 약간 작은데, 로더가 축퇴(degenerate) 폴리곤을 건너뛰기 때문이다.
따라서 **로더 버전이 바뀌면 이 값도 바뀔 수 있다** — 수락 기준은 이 표와의 일치가 아니라 §2의 그룹 구조·교차 확인으로 판정한다.

| 종류 | control points (FBX 원본) | 관측 `position.count` | 관측 삼각형 | 개수 |
|---|---|---|---|---|
| Rook | 740 | 4,428 | 1,476 | 4 |
| Queen | 11,742 | 70,029 | 23,343 | 2 |
| Knight | 24,978 | 149,070 | 49,690 | 4 |
| Pawn | 30,041 | 180,234 | 60,078 | 16 |
| King | 45,026 | 270,108 | 90,036 | 2 |
| Bishop | 59,530 | 356,628 | 118,876 | 4 |
| 보드 플레이 면 | 81 | 384 | 128 | 1 |
| 보드 프레임 | 5,776 | 34,200 | 11,400 | 1 |

핵심 성질(판별이 의존하는 것): **그룹 크기 집합이 {16, 4, 4, 4, 2, 2}로 유일하게 갈리고**, 정점 수 오름차순이
control point 기준과 `position.count` 기준에서 동일한 순서(Rook < Queen < Knight < Pawn < King < Bishop)를 유지한다.
높이는 King ≈ 5.515 > Queen ≈ 4.541. 보드 플레이 면 ≈ 23.650 × 23.650 → 셀 ≈ 2.956.

## 2. 슬라이스 0 — 에셋 전처리 (chess.fbx → chess-pieces.glb)

### 산출물

1. `web/tools/convert.html` (+ 전용 ts) — 브라우저 1회성 변환 페이지 (dev 전용, **게임 빌드에서 제외**)
2. `web/public/assets/chess-pieces.glb` — **말 6종만** (보드 제외). 용량 ≤ 3MB
3. `web/public/assets/chess-set.meta.json` — 단위·비율·충돌체 점 집합 메타 (스키마 아래 명시)

### 변환 페이지 동작 흐름

1. `chess.fbx` 드래그&드롭 (`File.arrayBuffer()` → `FBXLoader.parse()`) — 경로 하드코딩 없음
2. 단계별 상태 표시(파싱/판별/감축/내보내기), 중복 실행 방지, 오류 전문 표시, 실패 후 재시도 가능
3. 메시 인벤토리: 월드 AABB(중심·크기)·정점 수 집계 → 보드 2메시 우선 제외
4. **종류 판별 — 자기 보정 방식 (하드코딩 수치 금지)**
   1. 말 32개를 **동일 `position.count`끼리 묶어** 그룹화 → 그룹이 정확히 6개인지 확인
   2. 그룹 크기 집합이 **{16, 4, 4, 4, 2, 2}** 인지 확인 (아니면 즉시 중단·오류 표시)
   3. 크기 16 그룹 → `Pawn`
   4. 크기 4 그룹 3개를 **정점 수 오름차순** 정렬 → `Rook`, `Knight`, `Bishop`
   5. 크기 2 그룹 2개를 **정점 수 오름차순** 정렬 → `Queen`, `King`
   6. **교차 확인 2종** (판별과 독립된 근거로 검증)
      - 높이: `King` 대표 높이 > `Queen` 대표 높이
      - 백랭크 파일 위치: 백랭크 중심에서의 평균 절대 오프셋이 `Rook` > `Knight` > `Bishop`
   7. 교차 확인 실패 시 **변환 버튼을 잠근다.** 해제하려면 화면의 `위치·높이 경고를 확인했고 수동 지정으로 진행` 체크박스를
      명시적으로 켜야 한다 (v2의 "경고만 표시" 방식은 안전장치 역할을 못 하므로 폐기)
   8. 화면에 그룹별 라벨 + 대표 메시 3D 미리보기 + **그룹 단위(6개) 수동 재지정 드롭다운** 유지
5. 대표 메시 정규화 (그룹당 1개, 5단계 순서 고정):
   1. 완성된 `matrixWorld`를 지오메트리에 bake
   2. 월드 AABB의 x/z 중심을 원점으로 이동
   3. minY = 0으로 이동
   4. **킹 높이 기준으로 계산한 단일 전역 스케일을 6종 전체에 동일 적용** (킹 높이 = 1.0)
   5. 노드 TRS가 identity인지 검증
6. **감축(decimation)**: UV 등 불필요 속성 제거 → 정점 병합·index화 → 종류별 삼각형 예산으로 감축(meshoptimizer simplifier 권장, 차선 three SimplifyModifier) → 노멀 재계산
   - 예산: Pawn 3,000 / Rook·Knight·Bishop·Queen·King 각 5,000~8,000 삼각형

6-b. **감축 후 재정렬 (필수)** — 감축은 극점 정점을 제거할 수 있어 5단계 정규화 결과가 깨진다
   (게이트2 R2 실측: Knight `minY = 0.00022`, Pawn 중심 x `-0.000125` 등). 감축 **직후** 다시:
   - x/z 중심을 원점으로 이동, `minY = 0`으로 접지
   - 단언: `|center.x| ≤ 1e-6`, `|center.z| ≤ 1e-6`, `|minY| ≤ 1e-6` — 위반 시 종류 이름과 함께 중단
   - 이 재정렬이 끝난 지오메트리로만 bounds·충돌체 점·GLB를 만든다 (슬라이스 1의 스폰 높이·셀 중앙 배치가
     이 계약에 직접 의존하므로, 하류 코드가 오차를 보정하게 두지 않는다)
7. **충돌체 점 집합** (≤ 400개/종류, meta.json 저장, Rapier convexHull 입력용)

   **7-a. 바닥 평탄화 (게이트1 S1에서 추가 — 필수)**
   실측 결과 이 에셋의 말 바닥은 완전히 평평하지 않다. Pawn·Bishop·King은 **정중앙 한 점만 최저점**이고
   반지름 0.10~0.17 되는 바닥 링은 그보다 0.0007~0.0026 위에 있다(= 아주 얕은 아래쪽 원뿔).
   Rook만 평평하다(감축을 안 거쳤기 때문). 이 상태로 convex hull을 만들면 **말이 점 하나로 서게 되어**
   리뷰 Codex 사전 실측에서 10초 후 26/32만 잠들고 최대 기울기 6.67°였다(수락 기준 5초·2° 미달).
   - 규칙: `minY`에서 `BASE_FLATTEN_EPS` 이내인 정점의 y를 **정확히 `minY`로 스냅**한 뒤 중복 제거한다.
   - **후보값 사전 계산 (Claude, 현 GLB 기준)** — 값은 변환기 UI에서 조정 가능하게 두고 게이트2에서 확정한다.

     | eps | Pawn | Rook | Knight | Bishop | Queen | King |
     |---|---|---|---|---|---|---|
     | 0.003 · 바닥 hull 정점 | 30 | 20 | 20 | 49 | 20 | 23 |
     | 0.003 · baseRadius | 0.1336 | 0.1497 | 0.1759 | 0.1862 | 0.1355 | **0.1330** |
     | 0.004 · 바닥 hull 정점 | 30 | 20 | 20 | 58 | 20 | 45 |
     | 0.004 · baseRadius | 0.1336 | 0.1497 | 0.1759 | 0.1862 | 0.1456 | **0.1643** |

     둘 다 "hull 정점 ≥ 12"를 통과하지만, **King이 관건**이다. King은 높이 1.0으로 가장 높은데
     eps 0.003이면 바닥 지름이 0.266(높이 대비 27%), 0.004면 0.329(33%)다. 실제 체스 킹은 약 40%이므로
     **0.004가 더 사실적이고 더 안정적**이다. 두 값 모두 실척으로는 0.3~0.4mm 차이이고 콜라이더에만 적용된다.
     → 게이트2 브라우저 실측에서 0.003과 0.004를 §3-7 동일 기준으로 비교해 확정한다.
   - 이 스냅은 **충돌체 점에만 적용**한다. 렌더 메시는 건드리지 않는다(바닥은 판에 가려 보이지 않는다).
   - 스냅 후 바닥 평면 점들 중 **각도 균등하게 최소 12개**를 반드시 채택해 지지 다각형을 보장한다.
   - meta.json에 종류별 `baseRadius`(스냅된 바닥 점의 최대 반지름),
     `basePointCount`(샘플링 전 평탄화·중복 제거된 전체 바닥 후보 수),
     `baseFlattenEps`(실제 적용값), `baseHullPointCount`(2D 볼록껍질 정점 수)를 기록해 검증 가능하게 한다.

   **7-b. 나머지 점 선택**
   - **6축 극점(min/max x·y·z)을 반드시 포함**시킨 뒤, 남은 예산을 최원점(farthest-point) 방식으로 채운다
   - 이유: 균등 간격 샘플링은 극점을 떨어뜨려 충돌체가 시각 메시보다 작아진다(게이트2 실측: King y 범위가
     `0..1` → `0.0026..0.9729`로 축소, Rook max x `0.1664` → `0.1582`). 말이 서로 살짝 겹치거나 판에 파묻히는 원인이 된다
   - 검증: 충돌체 점들의 AABB가 감축 메시 AABB와 각 축에서 동일해야 한다 (오차 ≤ 1e-6). 위반 시 중단
8. `GLTFExporter.parseAsync({binary:true})` → GLB 다운로드 → `public/assets/`에 수동 배치. Three.js 버전 고정(package.json 정확 버전).

## 3. 슬라이스 1 — 보드 + 32말 + 물리 정지 안정 (v7, 슬라이스 0 실측 반영)

### 3-1. 월드 스케일 규약 — **1 unit = 1 m + 시간 배속** (v7, Claude 헤드리스 실측으로 확정)

> v6까지의 "1 unit = 0.1 m, 중력 −98.1" 규약은 **실측으로 틀렸음이 확인되어 폐기**한다.
> Claude와 독립 리뷰어가 Rapier 0.19.3에 실제 콜라이더 32개를 넣고 스윕한 결과,
> **중력 크기 `|g|`가 약 12 이하인 범위에서 안정적이며 g=−13부터 전원 정지 실패가 나타났다.**
> 표준 중력인 `−9.81`을 그 안정 범위 안의 안전한 고정값으로 선택한다.

**재현 조건:** 바닥 평탄화 eps 0.004, 20초 시뮬레이션, step 1/120, 반발 0,
linear/angular damping 2.0, 바디 생성 순서 = 백 1랭크 a1→h1 → 백 폰 a2→h2 →
흑 8랭크 a8→h8 → 흑 폰 a7→h7.

| 스케일 방식 | 잠듦 | 전원잠듦 | 최대 기울기 |
|---|---|---|---|
| king=1, g=−98.1, lengthUnit=1 | 27/32 | 미달성 | 3.70° |
| king=1, g=−98.1, lengthUnit=10 | 26/32 | 미달성 | 5.18° |
| **king=1, g=−9.81, lengthUnit=1** | **32/32** | **2.13초** | **0.86°** |
| king=0.1, g=−9.81, lengthUnit=1 | 24/32 | 미달성 | 5.34° |
| king=0.1, g=−9.81, lengthUnit=0.1 | 27/32 | 미달성 | 3.87° |

중력만 바꾼 추가 스윕에서는 −1부터 −12까지 모두 32/32가 잠들었고, −13부터 실패가 나타났다.
−15 / −20 / −30 / −50 / −98.1은 모두 26~31개에 그쳤다.
"중력 ÷ 스텝레이트를 수면 임계값 아래로 낮추면 된다"는 가설도 반증됐다 — g=−20을 1/240로 돌려
비율을 g=−9.81·1/120과 같게 맞춰도 27/32에 그쳤다. **문제는 비율이 아니라 중력의 절대값이다.**
즉 `world.lengthUnit`이나 중력/스텝 비율만으로 고중력 실패를 고칠 수 없으며,
표준 중력 −9.81은 검증된 약 −12 이내 안정 범위에서 충분한 여유를 가진다.

**따라서 규약을 이렇게 바꾼다.**

1. **물리 월드는 미터 단위로 돌린다** — `king = 1 unit = 1 m`, `GRAVITY_Y = -9.81`, `WORLD_LENGTH_UNIT = 1`.
   Rapier의 검증된 안정 범위 안에서 표준 단위와 표준 중력을 그대로 쓰는 안전한 설정이다.
2. **대신 시간을 배속한다** — `TIME_SCALE = Math.sqrt(10) ≈ 3.162`.
   중력 낙하는 `t ∝ √(L/g)`이므로, 1 m 물체를 √10배 빠르게 재생하면 **10 cm 물체와 똑같이 보인다.**
   물리 월드 자체는 건드리지 않으므로 안정성이 유지된다.
   루프에서 프레임 delta에 `TIME_SCALE`을 곱해 accumulator에 넣는 것이 전부다(§3-4).
3. `WORLD_LENGTH_UNIT`은 상수로 남기되 값은 `1`이다. Rapier 0.19.3에 `world.lengthUnit` API가 실재하지만
   (`node_modules/@dimforge/rapier3d-compat/pipeline/world.d.ts:105,121`), **실측상 이 문제를 해결하지 못했다.**
4. 손맛 튜닝 시 만지는 것은 중력이 아니라 **`TIME_SCALE`**이다. 중력은 −9.81에서 고정한다.

보드 크기는 4.556 unit이 되고, 화면상으로는 시간 배속 덕분에 45.6 cm 판처럼 읽힌다.

### 3-2. 절차 생성 보드

- 상판 = 8셀 + 사방 여백 0.25셀 = **8.5 × `cellSize` = 4.5560255** (한 변). 두께 = `boardThickness` = 0.158766.
- **여백은 완전히 평평하다. 턱·테두리 융기 금지** — 말이 판 밖으로 미끄러져 떨어지는 것이 승패 규칙이므로 걸림이 있으면 안 된다.
- **높이 배치 (수식으로 못박는다)**: 상면 y = 0, 판은 y = −`boardThickness` ~ 0.
  따라서 렌더 `BoxGeometry`와 물리 `cuboid` **둘 다 중심 y = −`boardThickness`/2, 반높이 = `boardThickness`/2**.
  고정 바디를 y=0에 두면 콜라이더 상단이 +두께/2가 되어 틀린다 (게이트1 S1 지적).
- **체크무늬 텍스처는 여백까지 포함해 그린다.** 8×8 캔버스를 전체 면에 늘리면 시각 셀이 0.5695가 되어
  물리 셀 0.536003보다 6.25% 커지고 여백이 사라진다 (게이트1 S1 실측).
  → 캔버스 = **테두리 16px + 셀 64px × 8 + 테두리 16px = 544px** (0.25셀 : 1셀 = 16 : 64 비율 일치).
  `BoxGeometry`의 면별 material group으로 **윗면에만** 이 텍스처, 나머지 면은 단색.
  `magFilter = NearestFilter`로 칸 경계를 또렷하게, `colorSpace = SRGBColorSpace`.
- 물리: **static 강체 + 상면과 정확히 일치하는 box 콜라이더 1개.**
  이 상면 경계가 슬라이스 3의 "판 밖" 기준면이 되므로, 반폭을 `BOARD_HALF_EXTENT`(= 4.5560255/2)로 노출한다.

### 3-3. 말 배치와 물리

- **좌표계**: x = 파일(a~h), z = 랭크(1~8). **백은 z 음수 쪽, 흑은 z 양수 쪽.** 카메라 기본 시점은 백 뒤편.
- **시작 배치**: 표준 체스. 백 1랭크 `R N B Q K B N R`, 2랭크 폰 8개, 흑은 8·7랭크에 거울 대칭.
  퀸은 자기 색 칸(d파일), 킹은 e파일 — 좌우 반전 실수를 막기 위해 배치 데이터를 파일 문자로 기술한다.
- 셀 중심 좌표 = `(file − 3.5) × cellSize`, `(rank − 3.5) × cellSize`.
- **강체**: dynamic. **회전 잠금 없음** — 넘어짐이 이 게임의 정체성이다.
- **콜라이더**: `ColliderDesc.convexHull(meta.pieces[type].colliderPoints)`.
  렌더용 고폴리 지오메트리를 직접 넣지 않는다. **반환값 null 검사 필수** — 실패 시 종류 이름을 포함해 중단.
- **질량·무게중심**: 개별 질량 상수를 두지 않는다. **단일 `PIECE_DENSITY` 상수만 두고 Rapier가
  `Collider.setDensity`로 hull에서 질량·무게중심·관성 텐서를 계산하게 한다.**
  - 정확히 말하면 이것은 실제 체스말(속이 비고 밑에 추를 넣음)의 물성이 아니라 **"균일 밀도로 채운 convex hull"의
    근사 물성**이다 (게이트1 S1 지적 — v5의 "실제 형상에서 정확한 무게중심"은 과장된 표현이었다).
    그래도 종류별 매직넘버 6개보다 낫다: 부피 차이로 킹이 폰보다 무거워지고, 비대칭 형상도 반영된다
    (density 1 기준 실측: Pawn 0.02261 / Rook 0.03689 / Bishop 0.04617 / Knight 0.05556 / Queen 0.06629 / King 0.08544,
    Knight 무게중심 x 오프셋 −0.01093).
  - **`PIECE_DENSITY = 1.2`** — 킹 질량 ≈ 0.103, 폰 ≈ 0.027이 되어 실제 체스말(킹 약 100 g, 폰 약 25 g) 수준이 된다.
  - 생성 후 종류별 `mass`, `localCom()`, 주관성 모멘트가 **유한하고 양수인지 검증·출력**한다.
  - 종류별 미세 조정이 필요해지면 슬라이스 2에서 density 배수를 추가한다(지금은 넣지 않는다).
- **재질 계수 (v7 실측 확정)**: 마찰 0.4, **반발 0.1**, **linearDamping = angularDamping = 2.0**.
  v6의 반발 0.2 + damping 0.5는 실측에서 29/32에 그쳐 폐기했다. 아래는 중력 −9.81·step 1/120 기준 스윕
  (eps 0.004, 20초, "통과" = 전원잠듦 ≤5초 · 기울기 ≤2° · 이동 ≤0.05 · 최저y ≥ −0.01 전부 충족):

  | 반발 \ damping | 1.0 | 2.0 | 3.0 |
  |---|---|---|---|
  | 0 | 5.88초 (미달) | **2.13초 통과** | 2.90초 통과 |
  | 0.1 | 2.14초 통과 | **4.02초 통과** | 2.13초 통과 |
  | 0.2 | 29/32 미달성 | 5.21초 (미달) | 2.13초 통과 |

  반발을 0으로 두면 말끼리 부딪힐 때 감각이 죽으므로 **0.1**을 택하고, 그 값에서 안전한 damping **2.0**을 쓴다.
  반발을 0.2로 올리려면 damping을 3.0으로 함께 올려야 한다(슬라이스 2 튜닝 시 이 표를 지킬 것).
  - **보드 콜라이더에도 동일한 마찰·반발을 설정한다.** Rapier 기본값은 마찰 0.5·반발 0이고 결합 규칙이 `Average`라,
    말에만 설정하면 실제 접촉값이 0.45/0.1이 되어 의도와 달라진다 (게이트1 S1 지적).
  - 전부 이름 있는 상수로 `config.ts` 한 곳에 모은다.
- **스폰**: awake 상태로 셀 중심, y = `SPAWN_GAP`. **sleep 상태 스폰 금지** — 겹침·부정확한 높이를 숨긴다.
  - 폐기된 중력 −98.1 구성은 한 스텝 낙하량이 기본 예측 거리보다 지나치게 커 첫 접촉 보정과 기울기를 악화시켰다.
    현재 구성은 표준 중력 −9.81과 바닥 평탄화를 함께 사용한다.
  - → `SPAWN_GAP` 기본값 **0**(바닥 평탄화 후에는 정확히 맞닿아 시작하는 것이 맞다). 게이트2에서 0과 0.001을 비교한다.

### 3-4. 게임 루프와 동기화

- Rapier는 `await RAPIER.init()` 완료 후에만 사용한다(`rapier3d-compat`는 WASM 초기화가 비동기).
- **`world.timestep = FIXED_STEP`을 명시적으로 설정한다.** accumulator만 고정하고 월드 timestep을 기본값으로
  두면 실제 적분 간격이 어긋난다 (게이트1 S1 지적).
- **accumulator 고정 스텝**: `FIXED_STEP = 1/120` 확정(실측 전 조합이 이 값 기준으로 통과했다).
- **시간 배속**: 프레임 delta에 `TIME_SCALE`(≈3.162)을 곱해 accumulator에 더한다(§3-1).
  물리 월드의 `timestep`은 그대로 `FIXED_STEP`이고, **한 프레임에 도는 스텝 수만 늘어난다.**
  필요한 스텝 수는 `120 × √10 ÷ fps`이므로 60fps에서 약 6.3, 30fps에서 12.6,
  24fps에서 15.8스텝이다. `MAX_STEPS_PER_FRAME = 16`으로 두어 24fps까지 정확한 시간 배속을 유지한다.
- 프레임 delta는 0.25 s로 clamp, 한 프레임 최대 스텝 수 제한. **한도를 넘긴 잔여 accumulator는 버린다**
  (누적하면 지연 후 폭주한다). 24fps 아래에서는 시간 빚을 누적하는 대신 의도적으로 슬로 모션으로 저하한다.
  이 정책을 코드 주석에 명시한다.
- 렌더는 `requestAnimationFrame`, 스텝 후 강체 `translation`/`rotation` → Three.js 메시로 복사.
  렌더 보간은 넣지 않는다(이번 슬라이스는 정지 화면이라 불필요 — 슬라이스 2에서 재검토).
- 리사이즈 시 카메라 종횡비·렌더러 크기 갱신.

### 3-5. 화면 (임시 — 슬라이스 2에서 당구식 조준 뷰로 교체)

- 카메라: `PerspectiveCamera` + `OrbitControls`(damping 켬, 팬 끔). 초기 위치는 백 뒤 비스듬한 위.
- 조명: `HemisphereLight` + `DirectionalLight` 1개(그림자 켬, 보드 전체를 덮는 shadow camera 범위).
- 말 재질: 백 = 밝은 회백색, 흑 = 짙은 회흑색. `MeshStandardMaterial` 2개를 32말이 공유.
- 지오메트리는 GLB의 6종을 공유하고 **말마다 개별 `Mesh` 32개**를 만든다(InstancedMesh는 불필요한 복잡성).
- **흑 기물은 Y축 π 회전**으로 배치한다. Knight는 좌우 비대칭이라 회전을 안 주면 양쪽이 같은 방향을 본다
  (게이트1 S1 지적). 단 **기울기 측정에서는 이 yaw를 제외**해야 한다(§3-7).
- **에셋 URL은 `import.meta.env.BASE_URL` 기준으로 만든다.** `"/assets/..."` 같은 루트 절대 경로는
  GitHub Pages 하위 경로 배포에서 깨진다 (게이트1 S1 지적).
- GLB 로드 시 **6개 Mesh와 POSITION 속성 존재를 검증**하고, 없으면 이름을 포함해 중단한다.
- **개발용 오버레이**(좌상단 텍스트): FPS, 동적 바디 수, 잠든 바디 수, 최대 위치 이동량·최대 기울기,
  종류별 mass·무게중심. 게이트2 정량 검증에 그대로 쓰이므로 임시 코드가 아니라 정식 모듈로 만든다.

### 3-6. 파일 구조

파일을 잘게 쪼개면 작은 수정에도 여러 파일을 왕복하게 된다.

```
web/src/
├─ main.ts           부트스트랩(에셋 로드 → 씬·물리 구성 → 루프 시작)
├─ config.ts         GRAVITY_Y, WORLD_LENGTH_UNIT, FIXED_STEP, PIECE_DENSITY,

├─ assets.ts         GLB + meta.json 로드·검증 (BASE_URL 기준, 6종 Mesh·POSITION 확인)
├─ layout.ts         표준 시작 배치 데이터(파일 문자로 기술) + 셀 중심 좌표 계산
├─ scene.ts          렌더러·카메라·조명·OrbitControls·절차 보드·32개 Mesh

└─ loop.ts           accumulator 고정 스텝 루프 + 물리→렌더 동기화 + 디버그 수치 집계
```

### 3-7. 수락 기준 (게이트2 — 정량)

게이트1 S1 지적 8번을 받아 **측정 방법까지 못박는다.** "폭발", "관통 0건" 같은 표현은 정의가 없어 폐기했다.

| 지표 | 정의 |
|---|---|

| 이동량 | 스폰 위치에서 현재 위치까지의 **3차원 거리** |

### 이 프로젝트에 옮길 때의 원칙

**강화는 "숫자 버프"가 아니라 "물리 변화"여야 한다.** 이 게임이 실제로 시뮬레이션하는 것은 형상·무게·마찰·반발이고,
그것이 곧 손맛이다. 원본 콩트의 개그도 이미 물리적이다 — **룩을 뒤집으면** 접지면이 좁아져 잘 넘어지지만 멀리 미끄러진다.
공격력 +10 같은 추상 수치는 이 게임에서 아무 감각도 만들지 않는다.

후보(확정 아님, 손맛 검증 후 논의): 무게·크기 변경, 마찰/반발 변경, 형태 교체(나이트→유니콘),
말 뒤집기, 분열, 폰 제물, 거대 말 소환(뽕맛은 크지만 가성비는 나쁘게), 강화 실패 시 파괴.

### 지금(슬라이스 0·1) 설계에 반영할 것 — 3가지만

앞으로 말이 **개별적으로 변하는** 게임이 될 것이 확정적이므로, 지금 값싸게 열어둔다.
그 이상은 만들지 않는다(YAGNI).

1. **말 상태는 종류가 아니라 개체 단위로 관리한다.** `layout.ts`는 "칸 → 종류"가 아니라
   **말 개체 목록**(고유 id, 종류, 진영, 시작 칸)을 만든다. 강화 상태는 나중에 이 개체에 필드로 붙는다.
2. **바디·콜라이더 생성은 초기화 전용이 아니라 언제든 호출 가능한 함수로 만든다.**
   강화로 형상·무게가 바뀌면 콜라이더를 교체해야 한다. 최초 생성은 `createPieceBody(instance)`,
   기존 개체의 운동 상태를 보존한 교체는 `replacePieceBody(instanceId, colliderPoints, density)` 경로를 쓴다.
3. **에셋 계약을 "정확히 6개"가 아니라 "필수 6종을 포함"으로 완화한다.**
   나중에 유니콘·거신병 모델이 추가돼도 로더가 실패하지 않아야 한다.
   (슬라이스 0 산출물 검증은 지금도 6종 기준을 유지하되, 런타임 로더만 완화)

### 지금 결정하지 않는 것

강화 확률·실패 페널티·획득 방식·밸런스·연출은 **손맛(슬라이스 2)이 검증된 뒤** 논의한다.
튕기는 맛이 없으면 그 위에 무엇을 얹어도 살아나지 않으며, 동료 Unity 버전과의 비교 기준도 조작감이기 때문이다.
